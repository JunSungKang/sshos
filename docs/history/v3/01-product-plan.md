# sshOS(시오스) 제품 계획서 — v3

작성·조사 기준일: 2026-11-14. 목표 제품: 1.0.0. 상태: **연구를 반영한 전략·구현 명세 제안, 구현 미착수**.

영문 이름은 `sshOS`, 한글 이름은 `시오스`, 문서의 제품 이름은 `sshOS(시오스)`다. 제품 분류는 **Linux 서버용 SSH 작업 공간**이며, 최초 지원 서버는 **Ubuntu Server 24.04 LTS**다. Ubuntu 전용 제품명으로 바꾸지 않는다.

## 1. 이 판본의 효력과 읽는 순서

현재 유효한 계획은 이 문서, [개발 계획서](02-development-plan.md), [조사·포지셔닝 보고서](03-research-and-positioning.md), [기계 판독 명세](spec-v3.json)다. v1·v2 원문은 `docs/history/`에 보존한다. v2의 넓은 기능 목록은 v3 구현의 추가 요구가 아니다.

| 구분 | 내용 | 효력 |
| --- | --- | --- |
| U: 사용자 확정 | 이름, Electron, macOS·Windows, Ubuntu 24부터 시작, SSH 계정·키, 비동기 SFTP와 상시 진행률, 앱 자체의 OS형 느낌, OSS 기여·copyleft 목표, 의존성 MIT 우선 | 유지 |

이번 요청은 조사와 계획 개정이다. 코드 작성·의존성 설치·Git 초기화·서버 조작·공개 게시를 시작하지 않는다. 후속 구현 요청이 승인하는 판본과 실제 메시지를 기록한 뒤 SDD 개발을 시작한다. 구현자는 숫자·enum·지원 범위를 임의 확장하지 않는다. 충돌 또는 누락은 영향받는 요구 ID와 함께 명세 변경으로 처리한다.

## 2. 조사에서 얻은 결론

논문 6편과 실제 도구 8종을 조사했다. 원문·방법·표본·한계·저장소 활동·라이선스·이슈 출처는 조사 보고서의 P01–P06, O01–O08에 있다. 이 조사는 설치 후 성능 비교나 시장 규모 조사가 아니다.

1. 비동기 SFTP, 파일 탐색, 전송 큐, 여러 서버 연결은 이미 제공된다. WinSCP의 전송 큐와 Electerm의 전송 구현을 기본 품질 기준으로 삼는다. [WinSCP 큐](https://winscp.net/eng/docs/ui_queue), [Electerm](https://github.com/electerm/electerm)
2. Termix는 작업 공간·파일 관리와 단독 실행 가능한 데스크톱 구성을 제공한다. “SSH를 GUI로 만들었다”, “OS처럼 보인다”, “중앙 서버 설치가 없다”만으로 독자적인 제품이라고 설명할 수 없다. [Termix](https://github.com/Termix-SSH/Termix), [설치 방식](https://docs.termix.site/install/)
3. 관리자 연구는 작업 중단, 대상 문맥, 실행 후 확인 정보의 중요성을 보여준다. 초보자 수요나 sshOS의 효과를 입증하지는 않는다. P01·P03을 바탕으로 결과 근거와 재개 문맥을 제품 가설로 삼는다.
4. Capistrano의 release 전환·복구는 이미 알려진 방식이다. sshOS의 가설은 새로운 배포 알고리즘이 아니라 제한된 작업에서 파일·대상·서비스·관측·복원을 연결하는 사용 경험이다. [Capistrano 구조](https://capistranorb.com/documentation/getting-started/structure/)

**제안하는 약속:** “준비된 서버의 서비스 파일을 바꿀 때, 어느 서버에서 무엇이 바뀌었고 재시작·응답 확인이 어디까지 끝났는지 한 작업에서 확인한다.”

“모든 Linux 조작을 GUI로 제공”, “명령어를 몰라도 새 서버 구축 가능”, “안전한 무중단 배포”, “모든 변경을 되돌림”, “새 버전 기능 검증”은 1.0의 약속에 포함하지 않는다.

## 3. 한 사용자와 한 작업

### 3.1 주 사용자

운영 기반이 준비된 소규모 서비스의 저빈도 운영 담당자다. SSH 접속 정보와 교체할 산출물 파일을 전달받아, 대략 주 1회 이하 수동으로 교체한다. 서비스·계정·권한을 최초 설정할 관리자 또는 개발자가 별도로 존재한다. 이것은 인터뷰에서 확인할 모집 기준이며 실제 시장 분포를 의미하지 않는다.

대표 사례는 이미 설치된 systemd 서비스가 읽는 `app.jar` 또는 단일 실행 파일을 교체하는 경우다. runtime 설치·빌드·압축 해제·DB migration·여러 파일의 일괄 교체가 필요한 작업은 이 범위에 맞지 않는다. 서비스가 파일을 다시 읽는 방식, 데이터 호환성, health 경로의 적합성은 준비 담당자가 확인한다.

### 3.2 핵심 작업의 시작과 끝

- 시작: 등록된 서버와 서비스 슬롯을 선택하고, 로컬의 단일 산출물 파일을 고른다.
- 진행: 로컬 사본 생성 → SFTP 업로드 → 내용 검증 → 적용 전 확인 → 이전 파일 백업 → 파일 교체 → 재시작 요청 → 상태·HTTP 응답 관측.
- 정상 끝: **“파일 교체·재시작·응답 확인 완료”**와 각 근거가 기록된다.
- 실패 끝: 실패한 단계, 현재 파일의 관측 결과, 복원 가능 여부가 표시된다.
- 단절 끝: **“결과 불명 · 다시 확인 필요”**로 남는다. 재접속으로 관측을 복구하며 변경 명령을 자동 재실행하지 않는다.
- 복원 끝: **“이전 파일 복원 확인”**, **“재시작 확인”**, **“응답 확인”**을 각각 판정한다.

정상과 장애 흐름 모두 GUI로 끝낼 수 있는 지원 범위를 검증한다. 지원 조건 밖의 복구는 관리자 작업으로 명시하고 성공으로 포장하지 않는다.

## 5. 지원 계약

### 5.1 환경

| 항목 | 1.0 지원값 |
| --- | --- |
| 클라이언트 | macOS 14 이상 arm64/x64, Windows 11 x64 |
| 앱 | Electron, 한국어 UI, 워드마크 sshOS |
| 서버 | Ubuntu Server 24.04 LTS amd64/arm64, 실제 systemd PID 1 |
| 접속 | 직접 SSH, SFTP subsystem, 비밀번호 또는 키 파일 |
| helper | `/usr/bin/python3` 3.12.x와 표준 sqlite3(SQLite 3.45 이상 4 미만), SSH 실행 채널의 일회성 코드 |
| 파일시스템 | 원격 로컬 ext4, 슬롯과 stage·backup이 같은 filesystem, fsync 가능 |
| 서비스 | system manager의 구체적인 `.service`, Type=simple 또는 exec, Restart=no, 적용 전 active/running |
| 응답 | 원격 서버의 `http://127.0.0.1:<port>/<path>`에 GET, 기대 status=200, 인증·redirect·TLS 없음 |
| 권한 | 비root SSH 계정이 슬롯 소유, unit 조회·해당 journal 읽기, 사전 부여된 해당 unit의 비대화형 restart 권한 |

다른 환경은 **“지원 조건 미충족”**으로 차단한다. 탐지 실패를 지원 확인으로 간주하지 않는다. 컨테이너·WSL·네트워크 filesystem·jump host·SSH agent·keyboard-interactive·MFA는 1.0 공식 지원에서 제외한다. 동일 API가 우연히 동작해도 지원 목록을 확대하지 않는다.

서비스 준비는 별도 문서로 관리자가 수행한다. 앱이 패키지·sudoers·unit·방화벽을 자동 수정하지 않는다. SSH 로그인 비밀번호 지원과 sudo 비밀번호 입력 지원은 별개다. v3의 sudo는 지정된 restart 명령에 대한 NOPASSWD만 지원한다.

### 5.2 서비스 슬롯

슬롯 하나는 `server identity + canonical directory + artifact basename + unit + health path`의 결합이다. 한 서버에는 슬롯 하나, 연결 프로필은 최대 10개 저장, 동시 연결은 최대 3대다.

- 디렉터리와 artifact는 사전에 존재해야 한다. artifact는 1 byte 이상 2 GiB 이하의 단일 일반 파일이다.
- 루트 `/`부터 슬롯까지 symlink를 허용하지 않는다. artifact hardlink 수는 1이어야 한다.
- 슬롯·artifact 소유 UID는 로그인 UID와 같고 artifact GID는 로그인 기본 GID와 같다. 디렉터리는 group/other 쓰기 금지다.
- artifact에는 xattr·확장 ACL·setuid·setgid·sticky bit가 없어야 한다. 모드는 기존 파일의 하위 9개 permission bit를 보존한다. 소유자·그룹은 지원 계약과 일치한 상태로 유지한다. mtime·ctime·inode 값은 보존하지 않는다.
- 슬롯 하위 `.sshos`는 앱 전용 상태 영역이다. 최초 등록 시 이것이 이미 존재하면서 유효한 sshOS manifest가 없으면 덮어쓰지 않고 차단한다.
- 준비 담당자는 “외부 배포 도구·서비스·다른 계정이 슬롯 artifact를 수정하지 않는다”와 “DB/외부 데이터 변경을 필요로 하지 않는다”를 확인한다. 이는 운영 전제이며 프로그램이 부재를 증명할 수 있는 사실이 아니다.
- 다른 도구가 파일을 바꾸면 hash/metadata 검사에서 발견되는 경우 차단한다. 검사 직후 외부 변경까지 막는 compare-and-swap 보장은 제공하지 않는다.

이 제약은 초기 출시 범위다. 더 넓은 파일·서비스 유형은 수요와 별도 adapter 검사 후 명세를 새 판본으로 바꿔 추가한다.

## 6. 화면과 기본 사용성

앱 전체가 하나의 작업 공간이다. 서버마다 가짜 Desktop OS를 만드는 구조를 사용하지 않는다. 공통 상단 바, 앱 실행 막대, 화면 탭, 하단 작업 선반을 공유한다.

| 영역 | 고정 동작 |
| --- | --- |
| 상단 56 px | sshOS, 열린 화면 탭, 연결된 서버 수. 탭 최대 6개 |
| 왼쪽 88 px | 홈 / 연결 / 파일 / 작업 / 설정, 아이콘과 글자 병기 |
| 중앙 | 선택한 화면 하나. 작업 화면은 단계 목록·현재 결과·로그를 같은 화면에 배치 |
| 하단 112 px | 진행 중·확인 필요 작업 2개 요약과 전체 보기. 다른 앱에서도 유지 |

최소 앱 크기는 1120×760 CSS px, 기준 시안은 1600×1000이다. 색상은 배경 `#DCE7EB`, 실행 막대 `#102D35`, 패널 `#F8FAFB`, 본문 `#16313B`, 보조 `#526870`, accent `#087F78`, border `#D3DFE3`다. 본문 14 px, 제목 16 px, 모서리 12 px. UI 기본 글꼴은 OS 시스템 sans-serif다. 외부 글꼴 번들은 추가하지 않는다.

자유 이동·겹침·내부 최대화·최소화는 구현하지 않는다. 탭을 닫아도 진행 중인 작업은 멈추지 않는다. 마지막 앱 종료는 진행 중 작업 수를 보여주고 `계속 사용` / `앱 종료`를 선택한다. 종료가 원격 변경의 취소를 보장한다고 표시하지 않는다.

모든 원격 화면과 확인 대화상자는 서버 이름·user@host:port·unit·artifact 경로를 표시한다. 시작된 작업의 대상은 불변이다. 사용자가 다른 서버를 클릭해도 대상이 바뀌지 않는다.

### 6.1 파일 앱

트리와 목록은 동일한 탐색기의 두 영역이다. 별도 앱·별도 탐색 모드를 만들지 않는다. 등록 슬롯 루트와 하위 디렉터리만 표시하며 `.sshos`는 일반 탐색에서 제외한다. 디렉터리는 탐색만, 일반 파일은 단일 다운로드만 지원한다. symlink·특수파일은 종류와 “지원 안 됨”을 표시하고 따라가지 않는다.

목록은 이름·크기·수정 시각·유형을 제공한다. 정렬은 이름 오름차순, 폴더 우선이며 클릭으로 열 방향 전환이 가능하다. 검색은 현재 디렉터리에 이미 불러온 이름의 부분 문자열만 필터한다. 숨김 파일 표시 토글은 기본 OFF다. 10,000개 항목을 넘으면 결과 잘림 경고와 작업 불가를 표시한다. 무한 재귀 탐색은 하지 않는다.

`새 파일 준비`는 로컬 파일을 골라 슬롯의 stage로 업로드한다. 업로드가 끝나도 live artifact는 바뀌지 않는다. 임의 경로 업로드·원격 생성·이름 변경·삭제·권한 수정·편집은 1.0에 없다. 다운로드는 OS 저장 대화상자에서 목적지를 정하고 기존 파일이 있으면 새 이름을 요구한다. 폴더 전송·이어받기·원격 파일의 OS 탐색기로 drag-out은 제외한다.

### 6.2 작업 앱

작업 화면의 단계는 `파일 준비 → 업로드 → 내용 확인 → 적용 대기 → 이전 파일 보관 → 파일 교체 → 재시작 → 응답 확인`이다. 단계별로 시간·관측·오류를 남긴다. `적용` 확인에는 old/new hash 앞 12자리와 전체 보기, 파일 크기, 대상, 일시 중단 가능성, 복원 범위를 표시한다.

상태·로그는 선택한 작업의 unit에만 연결한다. 별도의 시스템·프로세스·서비스 전체 목록 앱은 없다. 로그는 최근 200줄과 새로고침을 제공하며 화면당 1 MiB를 넘기면 잘림 표시를 한다. HTML·ANSI escape·제어 문자열을 실행하거나 링크로 자동 변환하지 않는다.

### 6.3 비동기 전송과 상시 진행률

전송은 UI와 별도 worker에서 실행한다. 전송 중 탭 전환·다른 서버 접속·파일 목록 탐색이 가능해야 한다. 전역 2개, 서버별 1개 byte transfer를 FIFO로 실행한다. hash 계산·백업·적용은 byte transfer 진행률에 합치지 않고 별도 단계로 표시한다.

250 ms 간격 이하로 과도하게 렌더링하지 않으며 데이터가 바뀌면 1초 이내 표시한다. byte 전송은 완료 바이트/전체 바이트, 백분율, 최근 3초 평균 속도를 표시한다. ETA는 표시하지 않는다. SFTP write ACK는 서버가 요청을 처리한 바이트이며 물리 디스크 저장률이 아니다. byte 수가 같아져도 내용 확인 전에는 “전송됨 · 내용 확인 중”이다. `파일 준비 완료`는 SHA-256 일치와 원격 fsync가 확인된 뒤 표시한다.

전송 취소·앱 종료·단절 시 이어받기는 하지 않는다. 재시도는 새 작업 ID로 0 byte부터 시작한다. 진행 중이던 apply·restore를 전송 재시도 버튼으로 반복하지 않는다.

## 7. 결과·예외·복원의 사용자 계약

| 상황 | 화면 결과와 허용 행동 |
| --- | --- |
| 최초 호스트 키 | fingerprint 확인 전 인증·전송 보류 |
| 저장된 키와 불일치 | 연결 차단. 설정의 명시적 신뢰 교체 절차만 허용 |
| SFTP/Python/권한/OS/슬롯 조건 실패 | 충족하지 못한 조건 표시. 자동 설치·권한 상승 없음 |
| 업로드 중 단절 | 전송 중단. live 변경 없음이 확인된 범위만 표시. 새 업로드 가능 여부는 journal 조회 후 결정 |
| 검증 실패·디스크 부족 | 적용 버튼 비활성, 새 파일 준비 또는 취소 |
| live 파일이 예상 hash와 다름 | 충돌, 적용·복원 차단. 원본을 임의 덮어쓰지 않음 |
| apply ACK 유실·worker 종료·원격 재부팅 | 결과 불명. 다시 확인만 자동화하며 재시작·교체를 자동 반복하지 않음 |
| 새 파일 확인, 재시작·HTTP 실패 | 각 결과 분리. 조건이 맞으면 이전 파일 복원 버튼 제공 |
| 다른 sshOS 작업의 잠금 | 진행 중인 작업 ID 표시. 강제 잠금 삭제 버튼 없음 |
| journal 파손·현재 파일이 old/new 어디에도 해당하지 않음 | 관리자 확인 필요. 변경 버튼 차단, 읽기·영수증 내보내기 허용 |
| 이전 파일 복원 후 HTTP 실패 | 파일 복원 확인과 서비스 응답 실패를 동시에 표시 |
| 로컬 기록 저장 실패 | 새 원격 변경 시작 금지. 이미 실행됐을 수 있는 변경은 결과 불명으로 재확인 |

`응답 확인`은 요청 당시 HTTP 200을 관측했다는 의미다. 업무 기능 정상, 데이터 정합성, 새 코드가 실제 응답했다는 의미가 아니다. `재시작 확인`은 성공한 명령의 영속 기록과 같은 boot에서 등록 unit의 새 InvocationID·active/running을 함께 확인했다는 의미다. PID 변경만으로 판정하지 않는다.

복원은 해당 작업의 이전 artifact 바이트·지원한 mode/owner/group을 되돌린다. DB·외부 API 호출·사용자 데이터·이미 보낸 메일·서비스 재시작의 부수 효과를 되돌리지 않는다. 자동 복원을 하지 않는다. 복원 전에도 대상과 hash를 확인받는다.

원격 백업은 최대 5개 보관하며 자동 삭제하지 않는다. 한도 도달 시 적용을 막고 설정에서 완료된 작업의 백업을 사용자가 삭제한다. 결과 불명 또는 진행 중 작업의 파일은 정리 대상에서 제외한다. 백업 삭제 후 해당 복원 버튼은 비활성화된다. 더 최신 작업이 같은 슬롯에 적용됐으면 이전 작업의 복원은 차단한다.

G2는 동일하게 준비된 서비스·권한·같은 크기 파일·두 서버 혼동 조건을 사용한다. 정상 1개, 교체 직후 ACK 유실 1개, 재시작 후 HTTP 실패와 파일 복원 1개로 총 3개 시나리오를 사용하며 도구별 동등한 안내를 제공한다. 장애 과업마다 대상 서버·현재 파일, 재시작 요청의 확인 결과, 현재 HTTP 관측, 확정할 수 없는 사실의 4개 질문을 한다. 참가자 1명의 장애 합격은 두 과업 모두에서 4개 질문을 모두 맞히고, ACK 유실 과업에서 거짓 완료를 선언하지 않으며, HTTP 실패 과업에서 도움 없이 파일 복원과 응답 재확인을 마친 경우다. baseline에서 스크립트·북마크 등 평소 기능을 인위적으로 막지 않는다. 시간에는 검증·복구와 필요한 창 전환을 포함하며 초기 설치/슬롯 준비 시간은 별도 보고한다. G3는 미지원 작업도 기록하여 좁은 범위 때문에 놓치는 기회를 숨기지 않는다. 소표본 결과를 전체 사용자에 대한 통계적 우월성으로 해석하지 않는다.

## 10. 라이선스·배포·기여

v2의 프로젝트 라이선스 계획 **AGPL-3.0-only**를 유지한다. 의존성은 기능·품질이 충족되는 MIT 후보를 우선 검토하고, 없으면 실제 통합·배포 방식에서 호환되는 OSI 승인 라이선스의 구성요소를 선택한다. 최상위 저장소의 license 이름만으로 전이 의존성·자산 권리를 판정하지 않는다.

AGPL은 이 코드를 포함하는 적용 대상 저작물의 배포 및 수정 버전의 해당 네트워크 상호작용 등에 의무를 둔다. sshOS로 접속한 서버의 독립적인 소프트웨어·업로드한 사용자 파일·단순 사용만으로 모든 코드가 공개되는 것은 아니다. 사용자의 공개 기여 목적을 이 범위 안에서 구현한다. [AGPL 원문](https://www.gnu.org/licenses/agpl-3.0.html)

배포본에 LICENSE, THIRD_PARTY_NOTICES, 정확한 commit의 대응 소스 archive·manifest를 포함한다. 설정의 `이 버전 소스 저장`으로 로컬에 내보낸다. CONTRIBUTING은 기여 권리·출처·동일 라이선스 조건을 명시한다. 상류 패치에는 원 프로젝트 라이선스·기여 규칙을 따른다. 실제 외부 PR 전송은 별도 요청 범위다.

내부 개발 alpha는 미서명 패키지를 허용하지만 사용자 pilot와 1.0 완료에는 macOS Developer ID 서명·공증 및 Windows 코드 서명 검증이 필요하다. 인증서가 없으면 해당 배포 검사를 미완료로 남기며 사용자에게 보안 차단 우회를 정규 설치 절차로 요구하지 않는다. 서명이 Windows 평판 경고를 항상 없애는 것은 아니다. [Electron 서명 안내](https://www.electronjs.org/docs/latest/tutorial/code-signing)

## 11. 완료 기준과 문서 관리

기능 완료와 제품 가치 검증을 구분한다. 실제 지원 OS·서버 조합의 필수 검사, 단절·충돌·복원 검사, 서명 패키지·소스 제공, G0–G3가 모두 충족돼야 1.0 완료를 선언한다. 계획서 구조 검사 통과는 제품 검사 통과가 아니다.

기계 명세의 R3-01–R3-32는 v3 전용 ID다. 과거 R01–R34의 의미를 덮어쓰지 않는다. v2→v3 대응표는 개발 계획서와 spec의 migration에 기록한다. 모든 제품 검사는 현재 `untested`, 구현 승인은 `pending`이다.

예상 화면의 프롬프트는 `design/preview-prompt.txt`를 v3로 갱신한다. 생성 이미지가 아직 없으므로 이미지 일치 검사를 통과로 표시하지 않는다. 이미지 도구의 기본 출력이 승인된 작업 루트 밖이라는 기존 제한은 유지된다. 구현 검증은 문서의 수치·행동 계약을 기준으로 하며 향후 생성 시안이 이 계약을 확대하지 않는다.
