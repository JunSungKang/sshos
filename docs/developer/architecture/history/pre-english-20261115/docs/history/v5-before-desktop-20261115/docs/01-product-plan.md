# sshOS(시오스) 제품 계획서 v5

기준일: 2026-11-14. 대상 제품: 첫 공개 버전 0.1.0. 상태: 계획 작성 완료, 제품 구현 미착수. 이 문서는 사용자가 확정한 Electron 선택과 온라인 오류 검색·AI 요약 제외를 반영한다. 제품 기능의 실행 계약은 [개발 계획서](02-development-plan.md), 검수 절차는 [기능·품질·보안 체크리스트](06-quality-security-checklist.md), 구현 작업자의 시작 지침은 [구현 인계서](07-implementation-handoff.md)를 따른다.

## 1. 제품의 역할과 문서 해석

sshOS(시오스)는 사용자의 PC에서 기존 SSH 계정으로 Linux 서버에 직접 연결하여 파일 작업을 수행하는 데스크톱 GUI다. 영문 제품명은 `sshOS`, 한글 이름은 `시오스`, 문서의 결합 표기는 `sshOS(시오스)`다. 서버에 데스크톱 환경을 설치하거나 서버 화면을 전송하는 제품이 아니다.

첫 버전의 주된 사용자는 SSH 접속 정보는 갖고 있지만 콘솔 명령에 익숙하지 않은 개인·소규모 서버 운영자다. 구현 목표는 `앱 실행 → 연결 등록 → 호스트 확인 → 인증 → 파일 탐색 → 파일 전송 → 진행과 결과 확인`을 명령어 입력 없이 완료하는 것이다. 초기 범위를 모든 Linux 명령어의 GUI화로 확대하지 않는다.

이 문서에서 ‘필수’는 해당 수용 기준을 통과해야 한다는 뜻이다. ‘제외’는 화면, IPC, 라이브러리 의존성, 통신, 설정, 비활성 실험 기능 중 어느 형태로도 이번 버전에 추가하지 않는다는 뜻이다. 숫자로 정한 한도·시간·지원 형식은 구현자가 변경할 수 없다. 요구사항 ID R01–R32와 검사 ID의 정본은 [spec-v5.json](spec-v5.json)이다. 사람이 읽는 상세 동작은 개발 계획서의 계약을 따른다. 문서 충돌은 구현자가 임의 해석하지 않고 관련 작업을 중단하여 충돌 위치와 해결안을 기록한다.

## 2. 사용자 결정과 첫 버전의 설계 범위

| 구분 | v5 결정 |
| --- | --- |
| 클라이언트 프레임워크 | Electron. Chromium은 GUI 전체를 렌더링하고 Node.js는 로컬 애플리케이션 처리에 사용한다. Tauri 병행 구현 없음 |
| 배포 경험 | Windows portable `.exe`, macOS ZIP 안의 `sshOS.app`. 설치 마법사와 사용자 개발 런타임 설치 없음 |
| 원격 구조 | 대상 서버의 기존 SSH/SFTP에 직접 연결. 중앙 관리 서버, 원격 agent, 전용 daemon, 전용 HTTP 포트 없음 |
| 기능 데이터 저장 | 사용자 PC의 JSON 파일과 OS 암호화. DB 서버, SQLite, ORM, IndexedDB, LevelDB를 앱 기능 저장소로 사용하지 않음 |
| 최초 지원 서버 | Ubuntu Server 24.04 LTS, amd64와 arm64 |
| 인증 | 사용자명+비밀번호 또는 사용자명+개인키. 개인키 passphrase 지원 |
| 전송 | 여러 일반 파일의 비동기 업로드·다운로드, 화면 이동 후에도 보이는 진행률 |
| 응답 표시 | 우측 상단의 현재 서버 연결 상태와 SSH 명령 응답시간 |
| 라이선스 | 프로젝트 AGPL-3.0-only. 의존성은 MIT를 우선하며 다른 호환 OSS도 검토 가능 |
| 이번에 철회한 아이디어 | 온라인 오류 검색, 숨은 브라우저 검색, 검색 API, AI 요약·에이전트·모델 연결. 향후 일정으로도 예약하지 않음 |

아래의 세부 한도와 파일 작업 축소는 사용자의 직접 발언이 아니라, 기존 파일 보존과 구현 범위를 명확히 하기 위한 이번 v5 설계 선택이다. 사용자 결정으로 오인하지 않는다. 새 파일 전달이 중심이며 기존 파일 갱신 용도로는 부족할 수 있다.

다음도 첫 버전에서 제외한다: 터미널, 임의 shell 명령, 서비스·프로세스·패키지·방화벽·Docker·DB 관리, 배포·롤백 자동화, SSH 터널·점프 호스트·에이전트 인증·다중요소 인증, 자동 재접속, 전송 이어받기·일시정지, 폴더 재귀 전송·삭제, 파일 덮어쓰기·내용 편집·권한 변경, 폴더 이름 변경·항목 이동·서버 간 복사, 링크·특수파일 조작, 플러그인, 팀 서버, 원격측 상태 DB, telemetry, crash report 업로드, 자동 업데이트. 일반 오류 코드를 한글로 설명하는 고정 문구는 필수이며 검색·진단 서비스로 확장하지 않는다.

v3의 Python helper, 원격 SQLite, 서비스 배포 슬롯과 복구 시스템은 폐기된 설계다. v4의 프레임워크 대기와 덮어쓰기 정책 미결정은 v5로 대체한다. 이력 문서는 구현 근거로 사용하지 않는다.

## 3. 지원 환경과 실행의 의미

| 위치 | 지원 계약 |
| --- | --- |
| Windows 클라이언트 | Windows 11 x64. Windows 10, Windows ARM64, Linux 클라이언트는 제외 |
| macOS 클라이언트 | 최소 실행 버전 macOS 14, arm64와 x64 배포물을 각각 제공. 최초 공식 검증은 macOS 14의 두 CPU 종류다. 추가 major는 해당 major·CPU 시험 통과 결과가 있어야 공식 지원 목록에 추가 |
| 대상 서버 | Ubuntu Server 24.04 LTS amd64/arm64의 보안 업데이트가 적용된 OpenSSH/SFTP. 설치·설정은 사용자가 이미 갖고 있어야 함 |
| 로컬 전송 목적지 | 해당 PC의 로컬 APFS(macOS), NTFS(Windows). 네트워크 드라이브·FAT/exFAT·클라우드 placeholder 목적지는 첫 버전 지원 제외 |
| 원격 업로드 목적지 | 기존 SFTP 읽기·쓰기 권한 및 OpenSSH hardlink 확장과 같은 디렉터리 내 hardlink가 허용되는 파일시스템. 불충족 시 업로드·파일 이름 변경만 제한 |
| 실행파일 | PC의 OS·CPU에 맞는 배포물을 선택. `.app` 내부 파일과 portable 실행 시 임시 해제 파일을 허용 |
| 사용자 추가 설치 | Node.js, Python, Rust, DB, 별도 Chromium, WebView2 설치를 요구하지 않음 |

Electron의 크기·메모리 비용은 없어지지 않는다. ‘가볍다’는 표현은 §9와 개발 계획서의 예산을 측정해 통과한 뒤 사용한다. Chromium 자체가 내부적으로 생성하는 캐시 파일의 형식까지 DB가 전혀 없다고 주장하지 않는다. 설정·기록은 실행파일 옆에 쓰지 않고 해당 OS 사용자 데이터 디렉터리에 둔다. portable은 설치 마법사가 없다는 뜻이며, 다른 PC로 복사한 암호문까지 복호화된다는 뜻이 아니다.

OS 탐지는 SFTP로 `/etc/os-release`를 읽어 수행한다. `ID=ubuntu`, `VERSION_ID=24.04`만 확인된 지원 OS다. 다른 OS가 확인되면 연결 정보를 표시하되 파일 변경·전송은 잠근다. chroot/SFTP-only 계정처럼 OS를 읽을 수 없으면 ‘OS 미확인’을 표시하고 연결마다 사용자가 ‘Ubuntu 24.04 서버임을 확인하고 파일 기능 사용’을 선택한 경우에만 파일 기능을 연다. 이는 자동 검증이나 다른 OS 지원 선언이 아니다. exec 제한은 응답시간 기능만 제한한다.

## 4. OS처럼 사용하는 작업 공간

하나의 앱 창에 홈·연결·파일·작업·설정 5개 영역을 둔다. 자유롭게 겹치는 내부 창이나 바탕화면 아이콘은 만들지 않는다. 파일 탐색의 트리와 목록은 한 화면의 두 영역이며 별도 앱·별도 모드로 나누지 않는다. 화면 전환 중에도 연결과 진행 중 작업을 유지한다.

| 화면 | 필수 내용 |
| --- | --- |
| 홈 | 등록 서버, 연결 상태, 진행·확인 필요 작업 요약. CPU·RAM 등 원격 모니터링 없음 |
| 연결 | 프로필 추가·수정·삭제, 인증 방식, 연결·해제, 호스트 지문 확인 |
| 파일 | 서버에 귀속된 탭, 폴더 트리, 경로 표시, 파일 목록, 업로드·다운로드·새 폴더·이름 변경·삭제 |
| 작업 | 작업별 대상 서버·경로·방향·진행·결과·고정 오류 설명. 현재 실행분과 보관 기록 구분 |
| 설정 | 한글 UI, 비밀정보 저장 선택, 로컬 기록 정리, 버전·라이선스. 검색·AI·원격 업데이트 설정 없음 |

최소 창은 1120×760 CSS px다. 상단 56px, 좌측 실행 막대 88px, 하단 작업 선반 112px를 예약하고 중앙만 스크롤한다. 기준 시안은 1600×1000이다. 배경 `#DCE7EB`, 실행 막대 `#102D35`, 패널 `#F8FAFB`, 본문 `#16313B`, 강조 `#087F78`을 사용한다. 상태는 문자와 아이콘을 함께 표시하고 색만으로 의미를 전달하지 않는다.

파일 탭은 최대 6개다. 서버·경로는 탭 소유 데이터이며 탭 전환으로 진행 중 작업의 대상이 바뀌지 않는다. 탭을 닫아도 전송은 계속된다. 하단 선반은 숨길 수 없으며 진행 중 최대 2개와 대기·오류 수를 표시한다. 전체 작업은 작업 화면에서 확인한다. 파일 목록은 가상 스크롤을 사용하고 키보드만으로 선택·이동·실행할 수 있어야 한다.

## 5. 연결과 파일 기능의 정확한 범위

프로필은 최대 10개, 동시에 연결되는 서버 프로필은 최대 3개다. 접속 주소·포트·사용자명·인증 방식을 명시한다. 포트 기본값은 22다. 처음 보는 서버의 SHA-256 호스트 지문을 보여 주고 사용자가 승인하기 전에는 비밀번호·인증 서명을 보내지 않는다. 저장된 호스트 키가 달라지면 연결을 차단한다. ‘무시하고 계속’ 버튼은 제공하지 않는다.

| 작업 | 허용 | 실패·제외 기준 |
| --- | --- | --- |
| 탐색 | 일반 폴더 이동, 트리 확장, 새로고침, 숨김 파일 표시, 이름·종류·크기·수정시각 조회 | 읽기 권한 없음, 안전하게 표현할 수 없는 경로는 설명과 함께 제한 |
| 업로드·다운로드 | 일반 파일 여러 개. 파일별 결과를 별도로 표시 | 폴더·symlink·장치·FIFO·socket, 이름 충돌, 지원하지 않는 파일시스템 |
| 새 폴더 | 현재 폴더에 단일 폴더 생성 | 같은 이름 존재 시 실패. 중간 부모 자동 생성 없음 |
| 이름 변경 | 같은 폴더의 일반 파일 1개를 새 이름으로 변경 | 폴더·링크·기존 목적지·다른 폴더 이동은 제외 |
| 삭제 | 일반 파일 1개 또는 빈 폴더 1개, 대상 확인 후 삭제 | 비어 있지 않은 폴더·링크·루트·재귀 삭제 제외 |
| 충돌 | 다른 이름 선택, 해당 파일 건너뛰기, 요청 취소 | 기존 목적지 삭제·덮어쓰기·자동 숫자 접미사 생성 금지 |

이름 변경은 새 이름 생성과 기존 이름 제거의 두 단계다. 중단되면 두 이름이 남을 수 있고 이를 ‘일부 처리됨’으로 표시한다. 모든 변경을 하나의 원격 트랜잭션처럼 되돌린다고 약속하지 않는다. 다른 프로그램이나 사용자가 같은 경로를 동시에 바꾸거나 서버 자체가 거짓 응답을 보내는 상황에 대해 원격 객체 동일성과 파일시스템 스냅샷을 보장하지 않는다.

새 업로드 파일의 요청 권한은 `0600`, 새 폴더는 `0700`이다. 원본 실행권한·소유자·ACL·확장 속성·수정시각을 복제하지 않는다. 다운로드도 원격 권한을 로컬 실행권한으로 복제하지 않는다. 파일 작업을 승인하기 전에 이 정책을 도움말에서 확인할 수 있어야 한다.

## 6. 전송과 완료의 의미

파일 전송은 UI와 별도인 비동기 엔진에서 수행한다. 전체 앱에서 동시에 최대 2개, 한 서버에서 최대 1개 전송을 실행한다. 앞선 작업이 서버별 한도에 막혀 있으면 다른 서버의 가장 오래된 실행 가능 작업을 먼저 실행한다. 각 파일은 별도 작업 ID를 갖는다.

업로드와 다운로드는 목적지 폴더의 임시 파일에 기록한다. 전송 내용의 SHA-256을 스트리밍으로 계산하고 임시 목적지를 다시 읽어 대조한 다음, 목적지가 존재하면 실패하는 hardlink 방식으로 최종 이름을 확정한다. 따라서 업로드 검증은 원격 파일을 한 번 더 읽는 트래픽이 발생한다. 속도보다 신규 목적지의 기존 파일 보존과 결과 구분을 우선한 선택이다. 상세 순서는 개발 계획서 §8을 따른다.

전송 선반에는 파일명, 서버, 방향, 전송 byte/전체 byte, 속도, 상태를 표시한다. `전송 중`, `내용 확인 중`, `최종 파일 생성 중`, `완료`를 구분한다. byte가 전체와 같다고 완료로 표시하지 않는다. 정상 완료는 데이터 대조, 최종 이름 확정, 상태 저장까지 확인한 상태다. 정전 후 디스크 영구 보존이나 전송 중 원본의 시점 스냅샷을 뜻하지 않는다.

중단·취소·프로세스 종료·응답 유실은 확인된 단계에 따라 분류한다. 원격에 변경 요청을 보냈지만 결과를 확인하지 못한 경우는 ‘결과 확인 필요’다. 자동 재실행·자동 이어받기·자동 원격 잔여 파일 삭제는 하지 않는다. 새로 연결한 뒤 위치를 열어 확인하고 필요한 행동을 사용자가 다시 선택한다. 명칭이 `.part`라는 이유만으로 파일을 삭제하지 않는다.

## 7. 우측 상단 연결 상태와 응답시간

파일 화면의 활성 서버에 대해 `production-01 · 연결됨 · SSH 응답 84 ms`와 같이 표시한다. 서버를 바꾸면 이전 서버의 숫자를 즉시 제거한다. 서버가 없는 화면은 연결된 서버 수와 서버 선택 UI를 표시하며 여러 서버 응답시간을 평균내지 않는다.

응답시간은 인증된 제어 SSH 연결에서 고정 `/bin/true` 요청 직전부터 정상 종료와 채널 닫힘을 확인할 때까지 측정한다. 로컬 큐 대기는 제외한다. 네트워크·SSH 채널·원격 shell·프로세스 처리 시간이 포함된다. **ICMP ping, 순수 네트워크 RTT, 서버 건강도 점수가 아니다.**

측정 종료 5초 뒤 다음 측정을 시작한다. 측정 기한은 5초, 서버별 미완료 probe는 최대 1개다. 15초 이상 지난 값은 숫자를 지우고 마지막 측정 시각만 설명창에 남긴다. 앱 비활성·최소화·절전 동안 새 측정을 멈춘다. 절전 복귀·재접속 시 이전 값을 폐기한다.

| 조건 | 표시 |
| --- | --- |
| 정상 | `SSH 응답 84 ms`, 1ms 미만이면 `SSH 응답 <1 ms` |
| 최초 요청 중 | `측정 중` |
| 5초 기한 초과 | `SSH 응답 지연` |
| exec 거절·명령 실행 실패·종료정보 없음 | `응답시간 측정 불가` |
| 채널 대기·앱 비활성 | `측정 대기`·`측정 일시 중지` |
| 연결 해제 | `연결 끊김`, 숫자 없음 |

고정 설명은 ‘현재 SSH 연결에서 짧은 명령의 완료 응답을 받는 시간입니다. 네트워크와 서버 처리 시간이 포함됩니다.’다. 측정 실패만으로 SFTP 전송을 끊지 않는다.

## 8. 저장과 신뢰 경계

프로필·호스트 신뢰·설정·작업 영수증은 PC의 사용자 전용 디렉터리에 JSON으로 보관한다. 영수증은 앱이 마지막으로 확인한 단계의 기록이며 원격 변경을 원자적으로 증명하는 서버 journal이 아니다. 비밀번호·passphrase 저장은 기본 꺼짐이다. 사용자가 켠 경우에만 Electron `safeStorage`로 암호화한 뒤 저장한다. 암호화 사용 불가 시 평문 저장으로 대체하지 않는다.

개인키는 사용자가 선택한 로컬 파일에서 읽으며 원격에 파일 자체를 보내지 않는다. 호스트 지문과 프로필 정체성을 확인한 연결에서만 인증한다. 원격 파일명·오류·배너는 실행 가능한 HTML·스크립트가 아닌 문자 데이터다. 사용자 작업 대상 외 웹사이트, 분석 서버, 검색·AI 서비스로 자동 요청하지 않는다. 앱은 HTTP 관리 서버를 열지 않는다.

비밀번호 입력창의 일시적 메모리와 OS가 생성한 메모리 덤프까지 완전히 제거한다고 주장하지 않는다. 같은 OS 계정을 장악한 악성 프로그램과 악성 서버에 대한 완전 방어도 제품 보장이 아니다. 이 경계를 이유로 입력 검증·암호화·호스트 확인·원본 보존 검사를 생략해서는 안 된다.

## 9. 품질과 실제 사용 가치의 검증

기능·보안 검사와 사용자 수요 검증을 분리한다. 모든 제품 검사는 현재 미실행이다. ‘결함 0개’라는 표현 대신 필수 검사의 통과 여부, 시험 환경, 미해결 결함을 기록한다. 개발 계획서 §14의 숫자는 목표 예산이며 실측 결과가 아니다.

- G0: 최근 3개월 SSH 파일 작업 경험자 6명을 인터뷰한다. 4명 이상이 첫 연결·전송 대기·화면 전환 후 대상 파악에서 실제 경험한 불편을 설명해야 문제 가설을 유지한다.
- G1: 지원 클라이언트 3종과 서버 CPU 2종의 조합에서 기능·보안·장애 시험을 수행한다. 압축·해제 크기, 첫 실행, 전체 앱 프로세스 메모리, 입력 반응, 전송 중 탐색을 측정한다. 정량 합격 기준은 개발 계획서 §14를 따른다.
- G2: 대상 사용자 12명이 평소 도구 조합과 시오스로 첫 접속·파일 전송·느린 응답·단절 확인 과업을 수행한다. 수행 순서는 각 6명씩 반대로 배정한다. 정상 과업 독립 완료 10/12 이상, 두 장애 과업 모두에서 현재 서버·확정 결과·미확정 결과를 정확히 설명한 사람 9/12 이상, 잘못된 서버 변경과 거짓 완료 0건을 요구한다. baseline의 기능을 인위적으로 제한하지 않는다. 기존 파일 갱신·폴더 전달이 필요한 작업은 미지원으로 별도 기록하고 삭제 후 재업로드를 성공 우회로 인정하지 않는다. 시간·도구 전환·결과 이해도 차이와 범위 제약 수용 여부를 함께 보고한다.
- G3: 6명에게 4주 pilot을 진행한다. 적합한 작업 기회가 2회 이상인 사람이 최소 4명이고 그중 최소 3명이 강제 없이 시오스를 총 2회 이상 사용해야 반복 사용 기준을 통과한다. 기회 부족은 실패가 아니라 관찰 부족으로 기록하고 수요를 입증했다고 발표하지 않는다.

내부 개발 빌드에는 G0–G3 통과를 요구하지 않는다. 외부 pilot 전에 모든 필수 기능·보안·품질 검사를 통과해야 한다. 0.1.0 정식 공개에는 필수 기술 검사와 G0·G2·G3 결과가 모두 있어야 한다. 미달을 숨기거나 기준을 완화해 같은 판본을 합격 처리하지 않는다.

## 10. 라이선스와 기여

프로젝트 자체는 `AGPL-3.0-only`로 배포한다. MIT는 의존성 선택의 우선순위이며 프로젝트 라이선스가 아니다. AGPL이 적용되는 코드·수정본의 배포와 해당되는 원격 상호작용에는 라이선스의 대응 소스 제공 조건을 적용한다. 단순히 시오스로 접속하거나 파일을 전송했다는 이유만으로 사용자의 독립 프로그램·서버 전체를 공개하도록 강제한다고 설명하지 않는다. [AGPL 원문](https://www.gnu.org/licenses/agpl-3.0.en.html), [GNU 원격 상호작용 설명](https://www.gnu.org/licenses/gpl-faq.en.html#AGPLv3InteractingRemotely)

의존성별 실제 LICENSE와 배포 조건, 수정 여부, transitive dependency를 확인한다. MIT가 아닌 경우에도 AGPL 배포와 양립하고 의무를 이행할 수 있는 OSS만 사용한다. 라이선스가 없거나 불명확하면 채택하지 않는다. 같은 릴리스의 소스, lockfile, 빌드 지침, 라이선스·고지, SBOM을 함께 제공한다. [MIT와 호환성 설명](https://www.gnu.org/licenses/license-list.html#Expat)

기여 정책은 CONTRIBUTING, SECURITY, CODE_OF_CONDUCT, 변경 기록, 테스트 절차를 포함한다. 오픈소스 공개와 GitHub 원격 변경은 실제 개발·배포 단계의 별도 작업이며 이번 문서 작성으로 수행한 것으로 표시하지 않는다.

## 11. 구현 순서와 납품 기준

개발 계획서의 D01–D10을 의존 순서대로 수행한다. 초기 기술 검증에서 signed portable 실행, safeStorage, SSH 키, SFTP hardlink, 스트리밍 해시 대조를 먼저 확인한다. 실패한 전제는 문서화하고 영향을 받는 작업을 멈추며 덮어쓰기 방식이나 서버 helper로 우회하지 않는다.

구현자가 임의 판단해야 하는 제품 기능 분기는 남기지 않는다. 인증서·실기기·시험 서버·공개 원격 저장소 같은 외부 자원은 개발 단계에서 확보해야 하는 선행 조건으로 별도 기록한다. 이번 납품물은 제품·개발 계획서, 체크리스트, 인계서, 기계 명세, 구조 그림과 문서 검사 결과다. 제품 코드·실행 빌드·실기기 검증·Git commit/push/merge는 아직 수행하지 않았다.
