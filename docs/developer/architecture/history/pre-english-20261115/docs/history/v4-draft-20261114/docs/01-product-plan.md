# sshOS(시오스) 제품 계획서 v4

2026-11-14. 상태: 공통 제품 요구 개정안, 프레임워크 사용자 결정 대기, 구현 미착수. 영문 이름 `sshOS`, 한글 이름 `시오스`, 문서 표기 `sshOS(시오스)`를 유지한다. 제품은 Linux 서버용 GUI SSH 작업 공간이며 최초 검증 서버는 Ubuntu Server 24.04 LTS다.

## 1. 확정 사항과 결정 대기 사항

사용자가 확정한 방향은 macOS·Windows GUI, SSH 계정·키 인증, 비동기 SFTP와 상시 진행률, 앱 자체의 OS형 작업 공간, 앱 기능용 DB 제거, 대상 서버 추가 프로그램 설치 없음, 실행 패키지를 받아 간편하게 시작, 상단 연결 상태·응답시간 표시다. OSS 기여와 copyleft 목표, MIT 우선 의존성 정책을 유지한다.

사용자는 Windows `.exe` / macOS `.app` 실행 형태를 수용한 뒤 Tauri와 Electron의 재비교를 요청했다. 따라서 프레임워크는 결정 대기다. [비교 문서](05-framework-comparison.md)를 기준으로 선택한다. 이전 Electron 선택을 재검토 요청 뒤의 최종 승인으로 간주하지 않는다.

v3의 단일 HTTP 서비스 배포·전용 슬롯·Python helper·원격 SQLite·배포 단계 복원은 철회한다. [v3 이력](history/v3/01-product-plan.md)은 과거 설계다. 이번 개정안의 공통 구조는 프레임워크 선택과 무관하게 적용하며, 선택에 의존하는 패키징·SSH 라이브러리·IPC 구현은 결정 후 고정한다.

## 2. 역할과 첫 사용자

시오스는 기존 SSH 계정으로 Linux 서버의 파일을 다루는 개인·소규모 운영자가 명령을 입력하지 않고 작업하고, 현재 대상과 전송·연결 상태를 계속 확인하는 데 집중한다. 기본 흐름은 `앱 실행 → SSH 연결 → 폴더 탐색 → 파일 전달·가져오기 → 다른 화면에서도 진행 확인 → 결과 확인`이다.

초기에는 파일 작업과 연결 가시성에 집중한다. 모든 Linux 명령의 GUI화, 원격 데스크톱, 서버 구축, 배포·복원 자동화, Docker·DB·패키지·방화벽 관리, 프로세스 종료, 서비스 시작·중지·재시작, 터미널, AI 실행, 플러그인, 팀 관리 서버를 포함하지 않는다. 서버별로 별도의 가상 Desktop OS를 띄우지 않는다.

## 3. 특장점과 검증할 가설

| 특장점으로 개발할 동작 | 사용자가 얻는 가치 | 감수하는 제약 |
| --- | --- | --- |
| 실행 패키지에서 바로 SSH 연결 | 전용 관리 서버·DB·서버 agent 준비가 없음 | SSH와 해당 기능의 기존 권한은 필요 |
| 서버·경로·작업이 유지되는 OS형 공간 | 화면을 바꿔도 어느 서버에서 무엇을 하는지 확인 가능 | 자유롭게 겹치는 내부 창은 초기 제외 |
| 상단 SSH 응답시간 + 하단 전송 상태 | 느린 응답과 진행 상황을 보고 기다림을 이해 | 지연 원인을 네트워크/서버 중 하나로 자동 단정하지 않음 |
| 기능별 지원 여부 표시 | exec 제한 계정에서도 가능한 SFTP 작업을 계속 사용 | 측정·일부 파일 작업이 제한될 수 있음 |
| 단절 후 결과 불명을 분리 | 확인되지 않은 변경을 완료로 오인하지 않음 | 자동으로 모든 작업을 되돌리거나 이어받지 않음 |

비동기 전송·파일 탐색·agentless 접근은 기존 도구에도 있다. Termix는 관리 서버 경유 방식과 데스크톱 내부 backend로 직접 연결하는 방식이 있고, XPipe도 원격 사전 설치 없이 동작한다. 시오스만 가능한 기능이라고 홍보하지 않는다. [조사 보고서](03-research-and-positioning.md)의 P01·P03은 작업 문맥과 확인 정보의 가설을 뒷받침하며 수요·우월성을 입증하지 않는다.

## 4. 실행과 의존성

| 위치 | 계약 |
| --- | --- |
| 사용자 PC | OS·CPU별 배포물 1개를 내려받아 실행. Node·Python·Rust·DB 서버를 사용자가 별도 준비하지 않는 것이 목표 |
| Windows | portable `.exe`. 설치 마법사·관리자 권한 요청 없음. runtime의 임시 해제와 사용자 데이터 파일은 허용 |
| macOS | 압축을 풀어 `sshOS.app` 하나를 실행. `.app` 내부의 여러 파일 구조 허용 |
| 대상 서버 | 기존 SSH. 파일 작업은 기존 SFTP subsystem 사용. Python·SQLite·시오스 daemon·관리용 HTTP 포트·전용 디렉터리 준비를 요구하지 않음 |
| 앱 기능 데이터 | 로컬 JSON 파일과 OS 암호화 기능. DB 서버·SQLite·ORM·IndexedDB를 기능 저장소로 사용하지 않음 |
| 앱 내부 | 검증한 SSH·암호화·UI 라이브러리를 포함할 수 있음. 개발 의존성과 사용자의 추가 설치를 구분 |

Electron의 내부 Chromium 저장소와 Tauri의 OS WebView 내부 데이터까지 물리적으로 DB 파일이 전혀 없다고 약속하지 않는다. 앱은 그 저장소를 기능 데이터 관리에 사용하지 않는다. 실행파일·서명된 앱 내부에 설정을 덧쓰지 않는다. portable은 설치 마법사가 없다는 뜻이며 암호화된 비밀정보를 다른 PC로 복사해 그대로 복호화할 수 있다는 뜻이 아니다.

Tauri 선택 시 Windows WebView2 존재 또는 동봉 정책을 먼저 확정한다. 작은 bare exe가 모든 Windows에서 추가 준비 없이 실행된다고 미리 약속하지 않는다. Electron 선택 시 runtime 묶음의 크기·해제 비용을 숨기지 않는다. 자세한 선택 조건은 비교 문서를 따른다.

## 5. 지원 범위와 기본 기능

공식 검증 대상은 macOS 14 이상 arm64/x64와 Windows 11 x64, 서버 Ubuntu Server 24.04 LTS amd64/arm64다. OS별 빌드·서명·실행 검사는 따로 한다. 같은 실행파일을 두 OS에서 그대로 사용하는 구조가 아니다.

SSH 인증 성공과 기능 지원 여부를 분리한다. SFTP가 없으면 파일 앱을 제한하고 연결 정보는 유지한다. exec가 거절되면 응답시간만 측정 불가로 표시한다. OS 탐지가 실패해도 인증 성공을 실패로 바꾸지 않으며 ‘OS 미확인’과 지원 보장의 범위를 알린다. 다른 OS는 공식 지원으로 홍보하지 않는다.

초기 기본 기능은 프로필 10개 저장·동시 연결 3대, 비밀번호와 암호화/비암호화 개인키, 호스트 지문 확인·변경 차단, 트리와 목록을 합친 파일 탐색, 여러 일반 파일의 업로드·다운로드, 새 폴더, 단일 항목 이름 변경, 단일 일반 파일·빈 폴더 삭제다. 자동 재접속·전송 이어받기·재귀 폴더 전송·재귀 삭제·파일 내용 편집·chmod/chown은 제외한다.

기존 파일 덮어쓰기와 메타데이터 보존 계약은 별도 설계 항목으로 남기며 구현 전 명세에서 고정한다. 기본 동작은 원본 보존이며 확인 없이 기존 파일을 덮어쓰지 않는다. 이 항목과 프레임워크별 구현이 고정되기 전 개발 착수용 명세를 승인 완료로 표시하지 않는다.

## 6. OS형 작업 공간

상단 56px, 좌측 실행 막대 88px, 중앙 작업 화면, 하단 112px 작업 선반을 사용한다. 앱은 홈·연결·파일·작업·설정 5개, 내부 탭 최대6개다. 탭은 서버와 경로를 유지하고 전송 수명은 탭 수명과 분리한다. 탭을 닫아도 전송은 계속된다. 앱 종료는 진행 작업과 결과 확인 필요 작업을 보여주고 종료 여부를 선택한다.

최소 창은1120×760 CSS px, 기준 그림은1600×1000이다. 배경 #DCE7EB, 실행 막대 #102D35, 패널 #F8FAFB, 본문 #16313B, accent #087F78. 서버와 경로·현재 작업은 문자로 식별한다. 색만으로 위험이나 상태를 구별하지 않는다.

현재 화면에 귀속된 서버의 상태를 **우측 상단**에 항상 표시한다. 예: `production-01 · 연결됨 · SSH 응답 84 ms`. 서버 문맥이 없는 홈에서는 연결된 서버 수와 서버 선택을 표시하고 여러 서버의 지연을 평균내지 않는다. 다른 서버 탭으로 바꾸면 해당 서버의 값으로 즉시 교체한다. 오래된 다른 서버 숫자를 잠시 재사용하지 않는다.

## 7. SSH 응답시간 표시

응답시간은 인증된 control SSH 연결에서 고정 `/bin/true` 실행 요청 직전부터 종료 코드0과 channel close를 확인할 때까지 worker의 monotonic clock으로 측정한다. 로컬 대기열 시간은 제외한다. 네트워크·SSH 채널·원격 shell과 프로세스 처리를 포함하며 **ICMP ping이나 순수 네트워크 RTT가 아니다**.

현재 화면의 서버만 즉시1회 측정하고 이전 측정 종료5초 뒤 다시 측정한다. 서버별 pending probe는1개, deadline5초, sample은 메모리에만 보관한다. 백그라운드·최소화·절전에서는 새 측정을 멈추며 복귀 시 예전 값을 폐기하고 다시 측정한다.

| 조건 | 표시 |
| --- | --- |
| 정상 sample | `SSH 응답 84 ms`; 반올림 정수,1ms미만은 `<1 ms` |
| 최초 측정 | `측정 중` |
| 15초 이상 된 sample | `SSH 응답 —`; 마지막 값·시각은 tooltip |
| 5초 초과 | `SSH 응답 지연`; timeout을 실제5000ms값으로 저장하지 않음 |
| exec거절/명령없음/exit정보없음 | `응답시간 측정 불가`; SFTP와 연결 유지 |
| 채널 예산 부족 | `측정 대기`; 사용자 작업 우선 |
| 연결 종료 | `연결 끊김`; 숫자 제거 |

숫자의 크기로 연결 종료나 서버 장애를 단정하지 않는다. 전송 중 sample에는 tooltip에 전송 중 측정임을 표시한다. 설명 문구는 ‘현재 SSH 연결에서 짧은 명령의 완료 응답을 받는 시간입니다. 네트워크와 서버 처리 시간이 포함됩니다.’로 고정한다. 측정 실패 때문에 전송 연결을 끊거나 측정용 채널을 무한히 추가하지 않는다.

## 8. 전송·기록·완료 판정

전송은 UI 밖 비동기 엔진에서 실행한다. control과 transfer SSH 역할을 분리한다. 전역2개·서버별1개 byte transfer를 FIFO로 실행한다. 하단 선반은 파일·대상·방향·byte 진행·속도·상태와 취소를 표시한다. byte 전송, 완료 확인, 완료를 분리하며 서버 write ACK를 정전 후 저장 보장으로 표현하지 않는다.

연결 끊김·worker 종료·앱 재실행 시 로컬 기록은 마지막으로 확인한 단계만 복원한다. 원격에서 실행됐는지 불명확하면 ‘결과 확인 필요’다. 변경 요청을 자동 재실행하지 않는다. 서버에 시오스 상태 DB나 영구 operation journal을 설치하지 않는다. 업로드 중인 파일의 임시 `.part`와 사용자가 요청한 산출물은 전용 서버 프로그램 설치와 구분한다.

설정·프로필·호스트 신뢰·작업 영수증은 로컬 JSON으로 저장하고 암호·passphrase는 OS 암호화 후 저장한다. private key를 원격으로 전송하지 않는다. 비밀·파일 내용을 telemetry로 보내지 않는다. 로컬 저장이 실패하면 그 사실을 표시하며 기록되지 않은 작업을 완료로 꾸미지 않는다.

## 9. 제품 가치와 가벼움 검증

아래는 향후 검증 설계이며 실측·수요 입증 결과가 아니다. 현재 조사 보고서의 숫자 정의는 이 절만 따른다.

- G0: 최근3개월 SSH 파일 작업 경험자6명 인터뷰.4명 이상이 첫 연결·전송 중 대기·화면 전환 후 대상 파악에서 구체적인 불편을 제시하는지 확인한다.
- G1: 최소 앱에서3개 client target의 압축 크기·해제 크기·최초 실행(Windows 해제 포함)·유휴/연결/2전송 중 전체 프로세스 메모리를 측정한다. 프레임워크 선택 후 수치 예산을 고정하며 실측 없이 ‘수MB·메모리50MB’ 등을 약속하지 않는다.
- G2: 대상 사용자12명이 평소 도구 조합과 시오스로 첫 접속·일반 파일 전송·느린 응답·단절 확인 과업을 수행한다. 순서는반반. 정상 독립 완료≥10/12, 두 장애 과업의 현재 대상/확정된 결과/미확정 결과 설명 모두정답≥9/12, 오대상 변경과 거짓완료0건을 요구한다. baseline 대비 첫 연결시간·도구전환·결과이해 차이를 모두 보고한다. 기능을 인위적으로 막은 baseline을 만들지 않는다.
- G3:6명4주 pilot. 적합 작업 기회2회 이상인 사람이4명 이상이고, 그중3명 이상이 강제 없이 총2회 이상 시오스를 사용해야 반복 사용 기준을 충족한다. 기회 부족은 관찰 부족이다. 미지원 작업과 기존 도구로 돌아간 이유를 숨기지 않는다.

기술 검증과 시장 검증은 구별한다. 기준 미달 시 기능을 무작정 늘리지 않고 원인을 평가한다. UI/전송 상태·SSH 응답 지표의 오류는 출시 전 수정한다. 기존 도구보다 반드시 낫다는 결론은 실제 비교 없이는 사용하지 않는다.

## 10. 라이선스와 남은 결정

프로젝트 AGPL-3.0-only 계획과 MIT 우선·호환되는 OSS 대안 정책을 유지한다. 독립 서버 소프트웨어·업로드 파일까지 공개 의무가 생긴다고 설명하지 않는다. 고지·대응 소스·기여 절차·서명된 배포 조건은 프레임워크 선택과 무관하게 유지한다. 개발·Git 초기화·공개는 이번 계획 작업에 포함하지 않는다.

현재 남은 결정은 프레임워크와 그에 연결된 runtime/SSH 라이브러리·검사 도구·자원 예산, 기존 파일 교체의 정확한 계약이다. [개발 계획](02-development-plan.md)과 기계 명세는 이 결정 이후 구현 착수 가능한 판본으로 마감한다. 공통 아키텍처 이미지는 [구조 문서](04-system-architecture.md)에 있으며 제품 실행 화면이나 성능 측정 결과가 아니다.
